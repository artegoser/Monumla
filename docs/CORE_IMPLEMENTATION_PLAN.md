# Monumla Rust Core Implementation Plan

## 1. Goal

Build a local-first Rust/WASM game runtime and a complete standard-chess ruleset, then expose the runtime to the existing Svelte frontend.

The first implementation is deliberately limited to standard chess as a playable product. The core architecture must nevertheless support future hard-coded custom pieces and abilities without requiring chess-specific concepts in the generic runtime.

The initial milestone explicitly does **not** include:

- AI/search or Stockfish integration;
- multiplayer/server authority;
- user-facing piece scripting or a DSL;
- procedural magic;
- fog of war;
- arbitrary graph topologies;
- large-board performance work.

The architecture must, however, already allow later pieces to:

- own arbitrary state such as HP, mana, cooldowns, stacks, or mode flags;
- inspect the current world and historical states;
- expose multiple abilities;
- perform multiple steps during one player turn;
- mutate any game state permitted by the rules runtime;
- change controller independently of owner;
- use more than two players/teams;
- emit semantic presentation cues while state changes remain authoritative.

## 2. Architectural invariants

These rules are constraints for the implementation, not suggestions.

### 2.1 The generic core contains no chess rules

`monumla-core` must not contain concepts such as:

- pawn, knight, bishop, rook, queen, king;
- white/black as player identities;
- check/checkmate;
- castling;
- en passant;
- promotion;
- FEN/PGN/SAN.

Those belong to `monumla-games-chess`.

### 2.2 Players are IDs, not colors

The core uses stable identifiers:

```rust
PlayerId
TeamId
EntityId
EntityTypeId
AbilityId
ChoiceId
```

An entity has at least:

```rust
owner: PlayerId
controller: PlayerId
```

`owner` and `controller` are intentionally distinct so future control-changing mechanics do not require a state-model rewrite.

Chess may map `ChessSide::White` and `ChessSide::Black` to concrete `PlayerId`s, but the core must not assume two players.

### 2.3 History is first-class readable game data

Rules may inspect previous committed states and previous steps. History is not only an undo implementation detail.

For the first implementation, use full state snapshots. Chess states are small enough that simplicity and correctness are more important than delta/checkpoint optimization.

History must distinguish:

- committed turns;
- individual steps inside a turn;
- speculative states used only for legality checks.

Speculative legality probes must never enter committed history.

### 2.4 Do not store derivable chess rule flags during normal play

Normal chess gameplay must derive special rights from entity state and history wherever practical.

In particular:

- no authoritative `en_passant_target` field during normal play;
- no authoritative `castling_rights` bitset during normal play.

En passant is generated by the pawn by observing an adjacent enemy pawn and verifying from history that the adjacent pawn was the actor of the immediately preceding completed turn/step and moved exactly two ranks in its initial double move.

Castling is generated by the king using current state:

- king entity state reports `has_moved == false`;
- rook entity state reports `has_moved == false`;
- required cells are empty;
- the king is not currently attacked;
- transit and destination squares are not attacked.

FEN import is the exception because FEN carries compressed historical rights but not the real history. The importer may synthesize minimal historical/entity state consistent with the FEN fields. This compatibility logic must remain inside the chess import layer.

### 2.5 Rules mutate a working state directly

Do not require all gameplay semantics to be encoded through a closed central enum such as:

```rust
Effect::Move
Effect::Damage
Effect::Heal
...
```

A hard-coded rule must be able to mutate a transactional working `GameState` through safe runtime helpers and, when necessary, a controlled raw-state escape hatch.

Conceptually:

```text
(State, player choice)
        |
        v
 arbitrary Rust rule
        |
        v
      State'
```

This keeps the runtime open to mechanics that were not anticipated when the core was written.

### 2.6 State mutation is transactional

A rule never partially corrupts committed state.

For a step:

1. start from the current working state;
2. apply the selected rule to a transaction/working copy;
3. validate the resulting state/transition;
4. commit the step to the turn session only if valid;
5. record history and presentation/change information.

For the first implementation, cloning the compact state for speculative validation is acceptable. Optimize later only after profiling.

### 2.7 Changes and presentation are not gameplay authority

The authoritative result is the new state.

After a valid transition, the runtime produces structural change information for the frontend, for example:

- entity moved;
- entity added;
- entity removed;
- entity type changed;
- entity state changed;
- board/cell state changed.

This may be generated automatically from the before/after states or recorded by transaction helpers.

Rules may additionally emit optional semantic presentation cues, for example a future `fireball_cast` cue. Presentation cues may improve animations but must never be required to reconstruct correct game state.

### 2.8 A turn may contain multiple steps

Do not model a player turn as exactly one move.

Use a `TurnSession` with a mutable working state and zero or more committed steps:

```text
committed state
      |
      v
 TurnSession
      |
      +-- Step
      +-- Step
      +-- Step
      |
      v
 FinishTurn
      |
      v
new committed state
```

Standard chess normally completes a turn after one selected chess action. The generic core must not enforce that limitation.

This is required for future mechanics such as:

- move, then cast an ability in the same turn;
- checkers multi-capture chains;
- action-point systems;
- forced continuation after a capture;
- abilities that unlock additional choices after an earlier step.

Each subsequent choice is computed from the **updated working state**, not from the state at the start of the turn.

### 2.9 Frontend interaction is choice-driven

The Svelte frontend must not implement piece legality.

The core/ruleset returns available interaction choices. The frontend renders them and returns the selected opaque `ChoiceId` plus any required input.

The interaction model must be capable of expressing at least:

- select entity;
- select board position;
- select ability;
- select option (for example promotion piece);
- finish turn.

A simple chess piece can skip an explicit ability menu and immediately expose legal destination choices. A future multi-ability entity may expose `Move`, `Fireball`, `Teleport`, etc. through the same protocol.

### 2.10 Attack semantics are separate from movement semantics

Every chess piece rule must be able to expose attacked squares independently from movement destinations.

This is essential for:

- pawns;
- king safety;
- castling-through-check validation;
- pinned pieces and legal-move filtering.

Do not infer attacks from final legal moves.

## 4. Core data model

The exact concrete Rust layout may evolve during implementation, but the semantics should resemble the following.

```rust
pub struct GameState {
    pub board: Board,
    pub entities: EntityStore,
    pub players: PlayerStore,
    pub teams: TeamStore,
    pub turn: TurnState,
    pub ruleset_state: RulesetState,
}
```

```rust
pub struct EntityState {
    pub id: EntityId,
    pub entity_type: EntityTypeId,
    pub owner: PlayerId,
    pub controller: PlayerId,
    pub position: Position,
    pub state: EntityData,
}
```

The generic core deliberately has no built-in movement-history field. Whether movement history matters is a ruleset concern. Standard chess stores `has_moved` only in king/rook entity state because castling needs that persistent fact; pawns derive double-step eligibility from their current starting rank and en passant from committed history.

`EntityData` must provide an extension point for future typed/custom state without forcing unrelated entities to carry ruleset-specific fields.

The first board implementation may be a rectangular grid. Do not generalize to arbitrary graph topology in this milestone.

## 5. History model

Initial model:

```rust
pub struct History {
    pub turns: Vec<TurnRecord>,
}

pub struct TurnRecord {
    pub before: GameState,
    pub steps: Vec<StepRecord>,
    pub after: GameState,
}

pub struct StepRecord {
    pub before: GameState,
    pub after: GameState,
    pub action: RecordedAction,
}
```

Expose query helpers rather than forcing rules to search raw vectors manually:

```rust
history.previous_turn()
history.last_step()
history.state_turns_ago(n)
history.entity_turns_ago(entity, n)
```

History must be sufficient for:

- undo/redo;
- replay/debug inspection;
- repetition detection;
- en passant derivation;
- future history-dependent abilities.

## 6. Turn and interaction runtime

Use a working `TurnSession`:

```rust
pub struct TurnSession {
    pub actor: PlayerId,
    pub before: GameState,
    pub working: GameState,
    pub steps: Vec<StepRecord>,
}
```

A generic interaction cycle is:

```text
query choices
    |
player selects one
    |
resolve selection
    |
transactionally mutate working state
    |
record step
    |
query choices from new working state
    |
continue or finish turn
```

The API must not require the entire multi-step path to be known before the first step executes.

That property is required for checkers-like chains and state-dependent continuation abilities.

## 7. Rule interfaces

Do not overfit the exact trait signatures before the data model exists. The core must nevertheless expose three conceptual rule categories.

### Entity rule

Responsible for entity-specific behavior and interaction generation.

Chess examples:

- `PawnRule`;
- `KnightRule`;
- `BishopRule`;
- `RookRule`;
- `QueenRule`;
- `KingRule`.

### Ability rule

A future extension point for explicitly named abilities. Standard chess does not need a rich ability system, but the core must not make adding one require a state-model rewrite.

### Game/ruleset rule

Responsible for game-level constraints and outcomes, such as chess king safety, side-to-move, mate/stalemate, and draw rules.

Predetermined Rust rules should be able to register with the runtime without editing large centralized `match` statements throughout the core.

## 8. Chess implementation details

### 8.1 Basic movement

Implement pseudo-movement and attack generation for all six pieces.

Sliding pieces must stop on the first occupied square, including the occupied square as an attack/capture candidate when appropriate.

### 8.2 Pawn

Pawn behavior owns:

- one-square advance;
- initial two-square advance derived from the pawn being on its starting rank;
- diagonal attacks/captures;
- en passant;
- promotion initiation.

En passant must be derived from history, not an ordinary runtime flag.

At generation time a pawn checks that:

1. an adjacent enemy entity is a pawn eligible by chess geometry;
2. the immediately preceding completed opponent action moved that exact pawn;
3. its previous and current positions prove a legal two-square initial pawn advance;
4. the en-passant destination is otherwise geometrically valid;
5. applying the complete candidate transition does not leave the moving side's king attacked.

### 8.3 King and castling

Castling is generated by the king from current state.

Requirements:

- king entity state has `has_moved == false`;
- correct rook exists and its entity state has `has_moved == false`;
- cells between king and rook are empty;
- king is not currently in check;
- king does not pass through an attacked square;
- king does not finish on an attacked square.

Executing castling may mutate the king and rook in one chess action/step.

### 8.4 Promotion

Promotion requires an explicit interaction choice among:

- queen;
- rook;
- bishop;
- knight.

Promotion must work both for quiet pawn moves and captures.

The frontend receives the options from Rust; it does not decide which pieces are legal promotion targets.

### 8.5 Legal move filtering

Pieces generate pseudo-actions/choices. Chess legality then tests the resulting state.

A candidate is legal only if the moving player's king is not attacked in the resulting position.

This must correctly handle:

- pinned pieces;
- discovered checks;
- double check;
- king captures;
- en passant opening an attack line;
- castling restrictions.

## 9. Chess outcomes and draw rules

Implement enough rule state/history inspection for a complete standard game:

- check;
- checkmate;
- stalemate;
- resignation;
- resignation and mutually agreed terminal outcomes recorded in authoritative history;
- draw by agreement only once both players have made at least one move;
- threefold repetition claims both from the current position and by declaring a legal next move that would create the third occurrence;
- fivefold repetition as an automatic draw condition;
- fifty-move claims both after 50 moves by each player and by declaring the legal next move that would complete that threshold;
- seventy-five-move rule as an automatic draw condition, with checkmate precedence;
- sound dead-position recognition, with exact arbitrary blocked-position reachability kept as an explicit limitation rather than approximated.

Do not approximate repetition using only piece placement. The position key must include all information relevant to legal move possibilities, including side to move and effective special rights.

Because the runtime derives castling/en-passant rights from state/history, the chess repetition key must derive equivalent effective rights as part of the key calculation.

## 10. FEN compatibility

Move the existing TypeScript FEN parsing into Rust and implement both parse and serialize.

FEN is a compressed position format and does not contain full historical state. Import therefore needs a compatibility reconstruction layer.

### Castling fields

Use the FEN castling field to initialize king/rook movement metadata consistently with the advertised rights.

If a required king/rook is present but a right is absent, initialize state so that the missing right does not become available merely because both pieces occupy their original squares.

### En-passant field

When an en-passant target is present, synthesize the minimal immediately previous pawn state/action needed for the normal pawn-history rule to observe the preceding double advance.

Do not introduce a permanent global en-passant flag just to accommodate FEN.

### Limitations

When FEN cannot reconstruct real historical facts, retain only the minimum semantics required for correct continuation from the imported position. Do not pretend that exact pre-import history is known. Validate standard structural legality on import (piece/pawn counts, promotion feasibility, king legality, castling metadata, and en-passant consistency), while recognizing that FEN alone cannot prove arbitrary retrograde reachability.

## 11. WASM/browser API

Expose a narrow browser-facing handle. A possible surface:

```text
GameHandle
  new_game(ruleset_id)
  view()
  interaction()
  choose(choice_id)
  cancel_selection()
  undo()
  redo()
  history()

Chess-only compatibility/capability entry points:
  new_chess()
  from_fen(fen)
  from_pgn(pgn)
  fen()
  pgn()
```

The frontend receives serializable views rather than Rust internals.

Suggested output concepts:

```text
GameView
  board
  entities
  players
  active players / side
  check status
  outcome

InteractionView
  selectable entities/cells/options/abilities
  opaque choice IDs

TransitionView
  updated GameView
  structural state changes
  optional presentation cues
  next interaction state
```

Keep JS/WASM calls coarse-grained. The frontend should not call WASM for every tiny internal engine operation.

## 13. Testing strategy

Correctness is more important than feature count in this milestone.

### 13.1 Core tests

Test:

- stable ID/state operations;
- entity placement/movement/removal;
- owner/controller independence;
- history snapshot correctness;
- turn-session commit/rollback;
- multi-step turn support;
- choice resolution;
- structural state-delta generation;
- undo/redo.

### 13.2 Chess piece tests

Per-piece tests for movement and attacks, especially pawn movement versus attack semantics.

### 13.3 Special-rule regressions

Dedicated tests for:

- all castling directions;
- rook moved away and returned;
- king moved away and returned;
- castling through check;
- castling while in check;
- en passant from both sides;
- en passant only immediately after the double move;
- en passant exposing own king;
- every promotion target;
- promotion by capture;
- pinned pieces;
- discovered check;
- double check;
- king capture legality;
- checkmate;
- stalemate;
- repetition;
- fifty/seventy-five move rules;
- dead positions;
- FEN roundtrip and imported-right reconstruction.

### 13.4 Perft

Use standard perft as the main legal-move regression oracle.

At minimum verify the initial position:

```text
depth 1 = 20
depth 2 = 400
depth 3 = 8,902
depth 4 = 197,281
```

Add established special-rule perft positions covering castling, en passant, checks, and promotions. Keep expensive high-depth reference cases in an explicit release-mode slow correctness gate so `cargo test --workspace` remains suitable for the normal development loop; run the slow gate whenever move generation, history semantics, or special-move execution changes.

### 13.5 Architecture proof tests

Do not ship another game mode yet. Add internal test-only rules proving the generic runtime is not secretly chess-only.

At minimum prove that without changing `monumla-core` one can define a test entity/ruleset that:

- owns custom entity state;
- mutates another entity's state;
- exposes an explicit ability choice;
- performs move + ability as two steps in one turn;
- forces a second continuation step;
- reads an earlier historical state;
- uses more than two `PlayerId`s;
- changes `controller` independently of `owner`.

These tests are architectural guards, not user-facing features.

## 14. Implementation phases

### Phase 0 — Repository preparation

Introduce the Rust workspace alongside the current Svelte application without changing gameplay behavior yet.

Deliverables:

- root Cargo workspace;
- `monumla-core`;
- `monumla-games-chess`;
- `monumla-wasm`;
- browser build integration skeleton;
- documented development commands.

### Phase 1 — Generic world state

Implement IDs, positions, rectangular board, players, teams, entities, owner/controller, extension state, and core invariants. Ruleset-specific historical facts must not become generic entity fields.

No chess pieces yet.

### Phase 2 — History and turn sessions

Implement full snapshots, turn/step history, working `TurnSession`, commit/rollback, undo/redo foundations, and history query APIs.

### Phase 3 — Interaction protocol

Implement generic choice IDs and interaction requests for entity/position/ability/option selection and turn completion.

Verify multi-step turns using test-only rules.

### Phase 4 — Transaction and change tracing

Implement transactional mutation, safe state helpers, escape hatch policy, before/after structural change tracing, and optional presentation cues.

### Phase 5 — Rule registration and presentation metadata

Implement the generic entity/ruleset rule registration boundary and entity presentation metadata needed by the frontend.

### Phase 6 — Basic chess pieces

Implement standard initial chess position plus pseudo-movement/attack generation for all six pieces.

Do not add king-safety filtering until the raw geometry is thoroughly tested.

### Phase 7 — Attack maps and legal chess actions

Implement attacked-square queries, king location/safety, candidate-state legality filtering, check detection, and legal interactions.

### Phase 8 — Special chess moves

Implement:

- pawn double advance;
- en passant derived from history;
- king-side and queen-side castling derived from movement state;
- promotion and promotion interaction choices.

### Phase 9 — Game outcomes and draws

Implement mate, stalemate, authoritative resignation/agreement terminal turns, current and intended-move repetition/50-move claims, automatic fivefold/seventy-five-move rules, and sound dead-position handling.

### Phase 10 — FEN

Implement robust Rust FEN import/export, standard structural legality validation, and minimal synthetic state/history reconstruction for FEN castling/en-passant semantics.

### Phase 11 — WASM bridge

Expose the stable `GameHandle`, DTOs, interaction calls, transition/change views, history, undo/redo, and FEN APIs.

### Phase 12 — Svelte authority migration

Replace TypeScript piece/FEN/game-state authority with the WASM game handle while preserving existing board rendering/assets where practical.

### Phase 13 — Lichess-parity interactive local chess UI

Replace the temporary click-only board interaction layer with a first-class board UX that matches the standard Lichess game board as closely as practical while remaining an independent Monumla implementation. The detailed contract lives in [`LICHESS_BOARD_UX_SPEC.md`](./LICHESS_BOARD_UX_SPEC.md).

Phase 13 must include both click-to-move and drag-and-drop, Lichess-style quiet-dot/capture-wedge destination markers, selected/last-move/check/hover states, drag threshold + ghost + cancellation semantics, StateDelta-driven move/capture/special-move animations, board-local graphical promotion choices, orientation-safe hit testing, responsive geometry, status/history/undo/redo/FEN development controls, and complete local two-player play.

The frontend may own pointer/touch mechanics and visual state, but Rust/WASM remains the sole authority for legal destinations and committed state transitions. No Lichess board package is added as a dependency and no upstream implementation is copied into the project.

### Phase 14 — Correctness suite

Complete perft and special-rule regression coverage. Fix all discrepancies before treating chess support as complete.

### Phase 15 — SAN and PGN

Add SAN move generation and tolerant legal SAN resolution plus PGN main-line import/export, tag preservation, and authoritative terminal `Result` handling after legal move semantics and history are stable.

The detailed standard-chess coverage audit is maintained in [`CHESS_RULES_AUDIT.md`](./CHESS_RULES_AUDIT.md).

### Generic ruleset outcome architecture

Game completion is represented by core `OutcomeRule` implementations evaluated at ruleset scope, not by `EntityRule`. Entity rules may expose local semantic state that outcome rules inspect, but only the ruleset decides whether a state is terminal. `RuleRegistry` evaluates registered outcome rules in explicit registration order and returns the first `GameOutcome`. Standard chess exposes `ChessOutcomeRule` as an adapter over its existing checkmate/stalemate/draw evaluator. See [`GENERIC_OUTCOME_RULES.md`](./GENERIC_OUTCOME_RULES.md).

### Generic composable game-rule architecture

Use the ownership and composition model in [`GENERIC_GAME_RULES.md`](./GENERIC_GAME_RULES.md). Intrinsic entity mechanics remain on entity rules; match/variant/map/environment mechanics are independent ordered `GameRule`s. `GameRuleSet` may add top-level choices, transform/filter local choices, validate the current rule context, and handle choices introduced by a global rule. Forced local continuations receive global transforms but not unrelated global choices.

Standard pawn promotion is the first production proof: `Pawn` owns the trigger, legal target types, generic continuation choices, validation, and final entity-type mutation. `ChessInteractionRules` only coordinates a pending continuation and forwards its ephemeral-free `ChoiceInput`; it does not branch on the continuation `ChoiceKind`. SAN/PGN, perft, and direct execution resolve ruleset-modified continuations through those same generated choices instead of bypassing them with a second promotion-specific execution API. Choice presentation (`label`, `asset_key`) is stored separately from semantic `ChoiceInput` data.

### Phase 16 — Architecture proof


- checkers proves mandatory capture, forced multi-capture continuation, piece-local promotion state, and multiple authoritative steps in one turn;
- Go proves placement via entity spawning, group capture, pass stones, suicide rejection, full-history situational superko, multi-phase dead-group review, AGA territory/area scoring, komi, and handicap;

The built-ins share the architecture-proof role but may mature independently. `monumla-games-go` now targets complete digital AGA board/scoring semantics; see [`GO_RULES_AUDIT.md`](./GO_RULES_AUDIT.md). Production matchmaking, tournament administration, exhaustive external record formats, and mode-specific production polish remain separate concerns.


### Phase 17 — Generic action notation and deterministic replay

Implement the canonical ruleset-agnostic game record described in [`GENERIC_ACTION_NOTATION.md`](./GENERIC_ACTION_NOTATION.md). Persist the ordered authoritative choices that produced each committed turn without storing ephemeral `ChoiceId` values, replay them through the ordinary `InteractionDriver`, and keep SAN/PGN as a chess-specific human notation adapter rather than the universal record model.

The phase must prove replay for arbitrary abilities, multi-step turns, forced continuation, history-dependent mechanics, control changes, and games with more than two players without adding mechanic-specific variants to `monumla-core`.

## 15. Definition of done for the first core milestone

The milestone is complete when:

1. a standard chess game can be played entirely locally in the existing Svelte application;
2. all authoritative rules execute in Rust/WASM;
3. TypeScript/Svelte contains no move-legality implementation;
4. all standard chess rules and terminal/draw conditions are supported;
5. en passant is derived from pawn-observable history during normal play;
6. castling rights are derived from entity movement/current state during normal play;
7. history is available to rules and supports undo/redo;
8. the generic turn runtime supports multiple sequential steps even though normal chess mostly uses one;
9. the frontend receives structural change traces for animation;
10. the standard chess board matches the Lichess move interaction loop: click + drag, quiet dots + capture wedges, selected/last-move/check feedback, drag ghost/cancellation, rounded board clipping, and deterministic special-move animation;
11. perft and special-rule regression suites pass;
12. the built-in checkers, Go, and Go rulesets prove that adding non-chess entities/abilities does not require changing the generic core;
13. a canonical generic action record can replay arbitrary accepted choice sequences through the same interaction runtime.
14. terminal conditions can be supplied as generic ruleset-level outcome rules without modifying entity rules or core enums;
15. intrinsic entity continuations and ruleset-wide modifiers compose through generic `ChoiceSpec`/`GameRuleSet` APIs without mechanic-specific interaction branches.

Only after these conditions are met should work begin on AI/search, multiplayer authority, dynamic/user-defined pieces, procedural abilities, or additional game modes.
